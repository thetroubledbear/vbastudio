Getting started

There's no marketplace install yet — you build vbastudio once, from source, on your own machine. It takes about 15 minutes the first time. Nothing on this page assumes you've used VS Code, git, or .NET before; follow the sections in order.

Prerequisites

You'll needWhy
WindowsExcel automation only works on Windows.
Microsoft Excel (desktop)vbastudio drives a real, open Excel workbook — it isn't a substitute for Excel.
VS CodeWhere you'll edit, set breakpoints, and debug.
Visual Studio 2022 or the Build Tools for Visual Studio 2022, with the .NET desktop development workloadThe broker that talks to Excel is a C# project with COM references — it needs full MSBuild to compile, not just the dotnet CLI.
Node.js (LTS)Used to build and package the VS Code extension itself.
This repository, downloaded or clonedThere's nothing to install from a package manager yet — you're building straight from source.
⚠ One Excel setting to check first

Excel blocks automated access to the VBA project by default. In Excel: File → Options → Trust Center → Trust Center Settings → Macro Settings, check "Trust access to the VBA project object model." Without this, every step below fails with a permissions error.

Build the broker

The broker is the C# process that actually talks to Excel. Open a terminal in the repository's vbastudio/ folder and run: 

"C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\amd64\MSBuild.exe" VbaStudio.sln /p:Configuration=Debug /m

(Adjust the path if you installed a different Visual Studio edition or the Build Tools — look for MSBuild.exe under your install folder.) This produces: 

VbaStudio.DapServer\bin\Debug\net8.0-windows\VbaStudio.DapServer.exe

Note that path — you'll need it in Configure the server path.

Build the extension

From the repository's extension/ folder:

npm install
npm run compile
npm run package

This produces a file named something like vbastudio-debug-0.0.1.vsix in that same folder.

Install the extension

code --install-extension "C:\full\path\to\vbastudio-debug-0.0.1.vsix"

Then run Developer: Reload Window from the Command Palette (Ctrl+Shift+P) so VS Code picks it up.

Configure the server path

Open Settings, search for vbastudio.dapServerPath, and set it to the full path noted in Build the broker. You can also do this from inside VS Code — the Command Palette has "VbaStudio: Set DapServer.exe Path...", which opens a file picker directly.

Open your workbook

Open the workbook you want to work on in Excel — make it the active window, since vbastudio always targets whichever workbook currently has focus. Then open that workbook's folder (or any folder — the workbook's path is stored separately) as a workspace in VS Code.

Pull your code

Click the vbastudio icon in the Activity Bar (the far-left sidebar), then the cloud-download icon in its title bar — or run "VbaStudio: Pull Modules from Excel" from the Command Palette. This copies every module's current code into a new src/ folder, where you can read and edit it like any other project.

Run or debug

Three ways to run a procedure — pick whichever's fastest:

  • Click it directly in the vbastudio sidebar tree.
  • Click the VbaStudio button in the status bar (bottom right) and type its name.
  • Run "VbaStudio: Configure Launch Target" from the Command Palette.

To actually debug: open the module in VS Code, click in the gutter next to a line to set a breakpoint, then run the procedure. Execution stops there, and the Variables pane shows every local in scope.

Sync & stale warnings

Excel and your src/ folder are two independent copies until you explicitly sync them. Pull and Push both compare against a small manifest of what was last synced, so a one-sided edit fast-forwards automatically, while a real conflict — both sides changed since the last sync, and differently — is left untouched and reported instead of silently overwritten:

  • Pull brings disk up to date with Excel: modules Excel changed get written, modules you only edited locally are left alone, and modules deleted in Excel are removed from disk too — unless you'd also edited that file locally, in which case it's flagged as a conflict and kept.
  • Push brings Excel up to date with disk: files you changed get written, Excel-side edits you haven't pulled yet are left alone rather than clobbered, and files you deleted locally are removed from Excel too — except Document/sheet modules, which the VBE won't let you remove.

A conflict is never resolved automatically. VS Code shows a warning naming the module; resolve it by hand — pull or push whichever side should win — then sync again.

If you edit a file in VS Code and try to run it without pushing first, vbastudio warns you before running — it'll offer to push and run, or run the old code anyway. Nothing pushes automatically.

Architecture

vbastudio is two halves: a C# broker that automates Excel over COM, and a VS Code extension that talks to it. Neither half runs inside Excel — there's no add-in to install, no VBA references to add to your project.

Green: one-shot CLI calls (list/pull/push/stale). Blue: the long-lived DAP session over stdio. Amber: the blocking HTTP loop that is the breakpoint.

The blocking POST is the whole trick: Agent.Probe cannot return until ProbeServer answers, so holding that HTTP response is indistinguishable, from VBA's side, from a real breakpoint. See How debugging works and Agent.Probe wire protocol for the full mechanics.

PieceWhat it owns
VbaStudio.Core Pure logic, no COM: the VBA parser (procedure and parameter boundaries), the instrumenter (rewrites a procedure to inject probe calls), the sync engine (Pull/Push), and shared models. Fully unit-tested.
VbaStudio.Interop The COM layer: Runner drives Application.Run and watches for compile/runtime error dialogs; ExcelVbaProjectAccess reads and writes VBA modules through the VBIDE object model; ExcelShadowWorkbook makes a throwaway copy for debugging; DebugSession wires instrumentation, the shadow copy, and a probe server together for one debug run.
VbaStudio.DapServer A small executable with two jobs: speak the Debug Adapter Protocol over stdio (the same protocol VS Code uses for any debugger), and answer the one-shot CLI queries the extension shells out to — list, pull, push, stale.
extension/ The VS Code client: registers the DAP adapter, the sidebar tree, the module/procedure pickers, and the sync commands. Talks to the broker only by spawning it as a process — no shared code, no direct linking.

How debugging works

VBA has no debugger API to hook into from the outside — there's no equivalent of "attach and set a breakpoint" the way there is for most languages. vbastudio works around this by rewriting the target procedure before running it, in a throwaway shadow copy of your workbook so your real file is never touched mid-run.

Every executable line in the procedure you launch gets a call to Agent.Probe inserted before it. That call POSTs the current line number and every local variable's value to a small HTTP server the broker runs — and because that POST blocks synchronously until the broker responds, the blocking call is the breakpoint. If you haven't set a breakpoint on that line, the server responds immediately and execution continues at full speed. If you have, the server holds the response until you click Continue in VS Code. The VBA thread never knows the difference between the two.

This only instruments the one procedure you launch — calls it makes to other procedures run un-instrumented, at full speed. See Capabilities & limitations for what that means in practice.

Instrumentation rules

VbaStudio.Core/Instrumentation/Instrumenter.cs rewrites the target procedure one physical line at a time. The rules below are exact — each one exists because of a specific way VBA breaks if you probe naively:

  • Line continuations are joined first. A statement split across several physical lines with a trailing " _" is treated as one atomic unit — a probe is never inserted mid-continuation, and a single-line If x Then y is already atomic, so it needs no special case.
  • With/End With blocks are skipped entirely. The With and End With lines themselves get no probe, and nothing inside the block does either (tracked via a withDepth counter, so nested With blocks are handled correctly). The instrumenter has no expression evaluator, so it cannot resolve the With target to show it — skipping the block is preferred over showing wrong or partial data.
  • The line right after Select Case <expr> is suppressed. VBA treats any statement between Select Case and its first Case clause as a hard compile error. The Select Case line itself is still probed normally; only the following line — guaranteed by valid VBA syntax to be the first Case — is skipped.
  • A probe is suppressed after a line that ends with a continuation marker inside a comment. Whether VBA treats a trailing " _" inside a comment as continuing that comment onto the next line is genuinely ambiguous — the instrumenter could not confirm it empirically — so it suppresses defensively rather than risk a probe call being silently swallowed into a continued comment and never firing.
  • Only variables already in scope are captured. Parameters are valid from procedure entry; a local is only added to the capture list once its own Dim/Static/Const line has been passed, because Option Explicit makes VBA reject a forward reference to a not-yet-declared local as a compile error — confirmed live against real Excel during development.
  • Only the single launched procedure is rewritten. Calls it makes to other procedures are not followed or instrumented — see Capabilities & limitations.

Agent.Probe wire protocol

Each inserted call looks like Agent.Probe 7, Array("x", x, "total", total) — a globally unique integer ID (assigned sequentially across the whole instrumentation run) and a flat Variant array alternating each in-scope symbol's name and its current value, in parameter-then-locals declaration order. Agent.Probe itself lives in vba/modAgent.bas, injected into the shadow workbook as a module named Agent before the run starts.

On every call, Probe builds this JSON body and POSTs it synchronously:

POST http://localhost:8731/probe/
Content-Type: application/json

{"probe_id":7,"vars":[{"n":"x","t":"Long","v":"3"},{"n":"total","t":"Long","v":"9"}]}

t comes from VBA's own TypeName(). Object and array values are not serialized by value — they come through as <obj:ClassName> or <array:TypeName> placeholders, since the probe has no generic way to stringify either. The HTTP call uses WinHttpRequest with its send timeout set to 0 (infinite) — this is what makes the call block for as long as you're paused on that line, however long that is.

VbaStudio.Core/Debug/ProbeServer.cs is the other end: a background-thread HttpListener that parses the body, resolves probe_id back to its source module and line number via the instrumenter's own site map, and calls a delegate that decides Continue or Abort. The response is one of exactly two shapes: 

{"cmd":"continue"}
{"cmd":"abort"}

No breakpoint on the line: ProbeServer answers immediately and this whole sequence collapses to a few microseconds. A breakpoint is what makes it wait for a human.

Probe raises a VBA error (vbObjectError + 3000) on abort, which is how clicking Stop in VS Code actually halts a running macro — there's no way to interrupt a COM call from the outside, so the interruption has to come from inside the VBA thread itself. An unknown probe_id or malformed JSON body fails closed to abort rather than leaving the VBA thread's blocking HTTP call hanging forever.

DAP surface

VbaStudio.DapServer speaks a deliberately small slice of the Debug Adapter Protocol over stdin/stdout — enough for VS Code's generic debug UI, nothing more:

RequestWhat it does here
initializeDeclares capabilities to VS Code. No breakpoint-related capabilities (conditional breakpoints, function breakpoints, etc.) are advertised, since none are implemented.
launchResolves the target module/procedure, instruments it, creates the shadow workbook, starts the probe server, and — once everything is ready to accept breakpoints — sends the initialized event.
setBreakpointsVerifies each requested line against the instrumented procedure's actual probe sites and reports back which ones are real (see BreakpointVerifier).
configurationDoneSignals VS Code has finished sending its initial breakpoints; the macro run actually starts here.
threadsReports a single, fixed thread — VBA is single-threaded, so this is always a one-entry list.
stackTraceReports one frame: the current probe's module and line. No call-stack frames beyond it, since only one procedure is ever instrumented.
scopesReports a single Locals scope, backed by the current probe event's variable list.
variablesReturns the name/type/value triples captured at the current probe.
continueResolves the probe server's pending Continue response, letting the blocked VBA thread proceed.
disconnect / terminateResolves the probe server's pending response as Abort, then tears down the shadow workbook.

Events sent back to VS Code:

EventWhen
initializedEnd of launch handling, after breakpoint sites exist to verify against — not on initialize, which would race the client's first setBreakpoints call against a session that isn't ready yet.
stoppedA probe with an active breakpoint blocks; reason is always "breakpoint".
outputConsole/stderr lines from the broker surfaced into VS Code's Debug Console.
terminatedThe run finished, failed, or was aborted.

Requests this DAP server does not implement: next/stepIn/stepOut (stepping), evaluate (watch/hover expressions), and function or conditional breakpoints. See Capabilities & limitations.

CLI mode contracts

Outside the DAP loop, VbaStudio.DapServer.exe also runs as a one-shot CLI — this is what the extension actually shells out to for the sidebar tree, the pickers, and sync. Each mode attaches to the already-running Excel instance, requires an active workbook, prints one JSON line to stdout, and exits — a non-zero exit with a stderr line means it failed (no active workbook, no running Excel, or a COM error).

VbaStudio.DapServer.exe list

{"workbookPath":"C:\\...\\Reporting.xlsm","modules":[{"name":"modWork","procedures":["First","Second"]}]}

Only standard modules, only Public Sub/Function procedures where every parameter is optional (see Capabilities & limitations).

VbaStudio.DapServer.exe pull

{"success":true,"srcDir":"C:\\...\\src"}

Exports every module to <workbookDir>/src/<Kind folder>/<name>.<ext>.

VbaStudio.DapServer.exe push

{"success":true}

Writes every changed disk file back into the live VBA project.

VbaStudio.DapServer.exe stale <moduleName>

{"stale":true}
{"stale":false}

Compares Excel's current code for that module against the corresponding disk file. A module Excel no longer has (renamed or deleted since the last pull) is reported stale rather than erroring.

Anything else in args[0] — a typo, or stale with no module name — exits 2 immediately rather than falling through to the DAP loop, which blocks on stdin forever and would otherwise just hang.

Module kinds & encoding

Every module read from the VBA project is classified into one of four kinds, which determines both where it lives under src/ and which encoding round-trips it without corruption:

KindExtensionFolderEncoding
Standard.basModules/Windows-1252
Class.clsClasses/Windows-1252
UserForm.frmForms/Windows-1252
Document (sheet/workbook code-behind).clsSheets/UTF-8, no BOM

Document modules get UTF-8 instead of Windows-1252 because they're conventionally kept in version control alongside the rest of a modern codebase and diff more predictably that way; every other kind uses Windows-1252 to match what the VBE itself writes and reads, since that's the encoding .Export()/.AddFromFile() actually use under the hood.

Because Pull and Push move a module's entire source text — not a parsed and regenerated version of it — attribute lines like Attribute VB_PredeclaredId (default-instance classes) and Attribute VB_UserMemId = 0 (default members, For Each enumerators) survive a round trip unchanged, because they're just more text in the file being copied. VbaStudio.Tests/Sync/RoundTripCorpusTests.cs asserts this directly against fixture classes with a predeclared ID, a default member, and a custom enumerator.

Building vbastudio itself

Contributing needs a different build than Build the broker above, which only covers producing a working .exe. Working on vbastudio's own source splits into a fast, COM-free loop and a slow, COM-dependent one:

  • VbaStudio.Core and VbaStudio.Tests reference no COM interop at all — the parser, instrumenter, sync engine, and probe server are pure C#. These build and test with the plain SDK CLI: 
dotnet test VbaStudio.Tests
  • VbaStudio.Interop, VbaStudio.DapServer, and VbaStudio.Spike carry COM references (Microsoft.Office.Interop.Excel, Microsoft.Vbe.Interop) that only resolve through full MSBuild — dotnet build fails on these three. Use the same command as Build the broker: 
"C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\amd64\MSBuild.exe" VbaStudio.sln /p:Configuration=Debug /m
  • The extension is a standalone TypeScript project under extension/: 
npm install
npm run compile

There is no automated end-to-end test that drives real Excel — every COM-touching path (Runner, ExcelVbaProjectAccess, ExcelShadowWorkbook, DebugSession) is verified by hand against a running Excel instance, not by CI. If you change anything under VbaStudio.Interop/, plan to rebuild and manually re-run a debug session against a real workbook before calling it done.

Capabilities & limitations

What works today:

  • Real breakpoints and captured locals for any Sub or Function you launch directly.
  • Two-way sync between Excel and disk, with a stale-before-run guard, conflict detection (both sides changed since the last sync are flagged, never silently overwritten), and delete propagation in both directions.
  • Standard, class, document, and UserForm modules can all be pulled and pushed, including class attribute lines like VB_PredeclaredId and VB_UserMemId (see Module kinds & encoding).

What doesn't, yet — each of these is a real, known gap, not a hypothetical one:

  • No call-chain debugging. Only the procedure you launch is instrumented — anything it calls runs un-instrumented, at full speed, with no breakpoints inside it. See Instrumentation rules.
  • No stepping, watch expressions, function breakpoints, or conditional breakpoints. The instrumenter already places a probe on every line and the DAP server has no handlers for next/stepIn/stepOut/evaluate — see DAP surface. Wiring stepping up is mostly plumbing at this point, not a design problem.
  • Debug.Print still goes to the VBE's own Immediate Window, not to VS Code's Debug Console. Capturing it is an open problem — the Immediate Window isn't automatable the way dialogs are — and is explicitly deferred as a future spike, not started.
  • Only Public Sub/Function procedures in standard modules whose parameters are all optional can be launched directly. ModuleListBuilder filters the picker to these because Application.Run("Module.Procedure") — the only mechanism vbastudio launches through — cannot call a class member, cannot supply arguments, cannot address a Property at all, and per Microsoft's own documentation must target a Public procedure. Listing anything outside this filter produces a real, reproduced DISP_E_PARAMNOTOPTIONAL from Application.Run itself. Wrap what you want to debug in a small Public, parameterless (or all-optional-parameter) Sub if you need to reach it.
  • IsMacroRunning is a hardcoded stub. ExcelVbaProjectAccess.IsMacroRunning always returns false; the guard that should block a Push while a macro is actively running does not actually detect that condition yet. This is a deliberate, accepted gap, not an oversight.
  • VBProject.Mode is an unreliable "still running" signal in this VBE version. Runner logs (does not block on) a warning when the project isn't reporting design mode before or after a run. This was downgraded from a hard precondition after live testing showed the mode reading stuck at Break (raw value 2) even after Run > Reset, while Application.Run kept succeeding cleanly and repeatedly regardless — the warning is worth reading, but not proof anything is actually wrong.
  • Windows and Excel only. This drives a real, local Excel process over COM automation — there is no cross-platform path.
  • The probe listener is unauthenticated. ProbeServer binds only to http://localhost:8731/probe/ (loopback, never reachable from the network), but while a debug session is active, any other process running as you on the same machine could reach that endpoint — same trust boundary as any local debugger. There is no telemetry and no network activity beyond that loopback connection.

Troubleshooting

"Object doesn't support this property or method" / permission errors

Almost always the Trust Center setting above. Double-check "Trust access to the VBA project object model" is on, then fully close and reopen Excel.

MSBuild fails with a COM reference error

You're likely using dotnet build instead of full MSBuild, or your Visual Studio install is missing the .NET desktop development workload. The broker's COM references only resolve through full MSBuild.

"The target VBA project is not the active project"

Make the workbook the active window in Excel before running or debugging — vbastudio always targets whichever workbook currently has focus.
